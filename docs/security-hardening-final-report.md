# AMWAJ Security Hardening — Before / After Report

**التاريخ:** 14 أغسطس 2026  
**النطاق:** تحصين داخل المستودع فقط، مبني على خطة الإصلاح المرفقة ونتائج التدقيق الأمني السابق.  
**القيود المصانة:** لم يُغيَّر مخطط Supabase أو RLS أو سياسات التخزين أو إعدادات Auth أو المتغيرات البيئية أو إعدادات الإنتاج الحية. كما لم يُعاد بناء لوحة الإدارة أو Admin Copilot أو CRUD، ولم تُضف أي مكتبة خارجية.

## الملخص التنفيذي

نفّذ هذا العمل المعالجات التي يمكن تطبيقها داخل كود AMWAJ وإعداد Vercel الموجود في المستودع فقط. ركز التنفيذ على تقليل سطح المتصفح، تقييد إساءة استخدام واجهات الذكاء الاصطناعي العامة، ونقل مسار إرسال المراجعات العامة إلى تحقق خادمي محدود مع الإبقاء على RLS الحالي مصدر التفويض. لا توجد في هذا التقرير مطالبة بأن التغييرات نُشرت؛ فالتحقق النهائي من ترويسات Vercel ومسارات `/api` في بيئة منشورة يبقى خطوة لاحقة بعد النشر.

لم تُكتشف حاجة فعلية إلى Redux أو Zustand أو dependency أمنية جديدة. استُخدمت وحدات Node/JavaScript القياسية، واتسقت المعالجة مع إبقاء حدود التفويض قائمة في Supabase وطبقات الخادم، بدل محاولة استبدالها بقيود واجهة المستخدم. هذا يتوافق مع مبدأ OWASP بأن التحكم في الوصول لا يعتمد على العميل، وأن حوكمة مكونات الطرف الثالث جزء من أمن سلسلة التوريد.[1] [2]

| النتيجة | الوضع قبل التنفيذ | الوضع بعد التنفيذ | الحالة |
|---|---|---|---|
| ترويسات المتصفح وCSP | لم تكن CSP والترويسات الدفاعية مفروضة في إعداد Vercel المصدر | CSP محددة المصادر، HSTS، منع الإطارات، سياسة مرجع وصلاحيات، و`nosniff` | منفذ في المستودع |
| Font Awesome الخارجي | تحميل CDN ثابت بلا SRI | روابط CDN الثابتة المدرجة مدعومة بـSRI و`crossorigin="anonymous"` و`referrerpolicy="no-referrer"` | منفذ في المستودع |
| إساءة استخدام AI | غياب حدود خادمية موحدة لحجم الإدخال/المخرجات/المهلة وrate limit | تحقق بنيوي، حدود حجم وتكلفة، مهلة 25 ثانية، وrate limiter محلي | منفذ جزئيًا؛ انظر القيود |
| مراجعات العملاء | إرسال مباشر من العميل إلى Supabase مع تبريد متصفح فقط | `/api/reviews` يتحقق خادميًا ويستخدم honeypot وحدود IP ثم يمرر السجل إلى RLS القائمة | منفذ في المستودع |
| Supabase Auth: leaked-password protection | معطلة في البيئة الحية وفق التدقيق | لا تغيير؛ إعداد خارج المستودع | مخاطرة متبقية خارج نطاق الكود |
| RLS وAdmin authorization | محمية بـRLS/`private.is_admin()` ومسارات خادم سابقة | لم تُغيّر، واستمرا كحد التفويض الحقيقي | محفوظة بلا تغيير |

## Gap Analysis: الخطة مقابل findings التدقيق

الجدول التالي يطابق بنود خطة الإصلاح مع الدليل السابق وقرار التنفيذ. المقصود بـ **مثبت** هنا أن التدقيق السابق وجد الدليل في المصدر أو البيئة الحية، وليس مجرد احتمال نظري.

| بند الخطة | دليل التدقيق السابق | القرار | التنفيذ أو السبب |
|---|---|---|---|
| CSP وترويسات الحماية | مثبت: استجابة الإنتاج/إعداد المصدر لم يفرضا CSP كافية أو HSTS | نفذ | تحديث `vercel.json` بترويسات متوافقة مع مصادر التطبيق الفعلية |
| SRI للأصل الإداري الخارجي | مثبت: Font Awesome على CDN بلا تحقق تكامل | نفذ | إضافة SRI للروابط الثابتة المفحوصة دون تغيير الإصدار |
| Distributed AI rate limiting | مثبت: لا حد موزع عبر مثيلات serverless | نفذ جزئيًا | limiter محلي لكل مثيل فقط؛ لا إضافة خدمة خارجية دون حاجة/اعتماد جديد |
| Input/output cost controls | مثبت: مدخلات ومخرجات AI احتاجت حدودًا خادمية | نفذ | حدود رسائل وأدوات وسياق ومخرجات، ومهل upstream وتحسين معالجة الخطأ |
| إساءة استخدام المراجعات | مثبت: الاعتماد الفعلي كان على RLS وتبريد المتصفح، دون بوابة خادم | نفذ | endpoint خادمي يتجنب تجاوز RLS ويضيف تحققًا وhoneypot وrate limit |
| leaked-password protection | مثبت من إعداد Supabase Auth الحي | لم ينفذ | لا يمكن ضبطه بأمان من ملفات المشروع؛ يتطلب إعدادًا في Supabase Auth |
| CORS | ضعف: نقاط عامة تحتاج سياسة موحدة؛ لا توجد دلالة على تسريب صلاحية بسبب CORS | نفذ بشكل متوافق | طرق `POST, OPTIONS` وترويسات محتوى فقط وبدون credentials؛ أبقي `*` لأن APIs عامة وغير موثقة |
| Admin authorization | لا ثغرة: RLS ودالة فحص الدور ومسارات الخادم تفرض التفويض | لا تغيير | أي تعديل هنا مخالف لشرط الحفاظ على RLS/CRUD ويفتقر إلى مبرر تقني |

## What Changed

### 1. Browser and CDN hardening

أضيفت سياسة محتوى مفروضة إلى `vercel.json`. تقتصر `default-src` على المصدر الذاتي، وتحظر الكائنات المضمنة، وتمنع التضمين داخل الإطارات عبر `frame-ancestors 'none'` و`X-Frame-Options: DENY`. كما تضيف السياسة `Referrer-Policy: strict-origin-when-cross-origin` و`Permissions-Policy` لتعطيل camera وgeolocation وmicrophone وpayment وUSB، إضافة إلى `X-Content-Type-Options: nosniff` وHSTS لمدة سنتين مع `includeSubDomains`. تتبع هذه الترويسات النهج الذي توصي به وثائق Vercel لحماية المتصفح وتقييد المصادر.[3]

يستمر السماح بما يحتاجه التطبيق الحالي فقط: Tailwind CDN، وcdnjs وGoogle Fonts، وصور Unsplash، وSupabase، والسكربتات والأنماط المضمنة الحالية. وجود `'unsafe-inline'` في `script-src` و`style-src` هو **دين تقني مقصود ومعلن** للحفاظ على الصفحة الحالية؛ إزالته تتطلب فصل السكربتات والأنماط المضمنة واختبارًا وظيفيًا أوسع، لذلك لم يُنفذ كتغيير تجميلي عالي الخطورة.

| الترويسة أو الأصل | Before | After |
|---|---|---|
| Content-Security-Policy | لا سياسة مفروضة | سياسة allowlist مفروضة في `vercel.json` |
| HSTS | غير موجودة في المصدر | `max-age=63072000; includeSubDomains` |
| حماية clickjacking | `SAMEORIGIN` فقط في المصدر | `frame-ancestors 'none'` و`X-Frame-Options: DENY` |
| Font Awesome CDN | رابط بلا SRI | SRI + `crossorigin="anonymous"` + no-referrer على الروابط الثابتة المفحوصة |

### 2. Public AI API abuse and cost controls

أضيفت وحدة صغيرة مشتركة في `api/_lib/public-api-security.js` لاستخراج عنوان العميل من رأس Vercel المفضل، تطبيق ترويسات CORS العامة المتسقة، تحليل JSON بحد حجم، rate limit محلي بذاكرة العملية، وإلغاء upstream بعد انتهاء المهلة. لم تُخزن أي بيانات حساسة أو مفاتيح في الواجهة؛ تبقى مفاتيح مزودي الذكاء الاصطناعي في متغيرات بيئة Vercel فقط.

استُخدمت هذه الوحدة في `api/chat.js` و`api/trip-planner.js`. المحادثة تقبل حتى 10 طلبات لكل عنوان IP في الدقيقة، وبحد 64 KiB للطلب، و12 رسالة، و16,000 حرف إجمالي، ومخرجات بحد 800 token، ومهلة upstream قدرها 25 ثانية. Trip Planner يقبل حتى 5 طلبات لكل IP في الدقيقة، وبحد 64 KiB، وسياق أعمال بحد 24,000 حرف، ومخرجات بحد 1,600 token، والمهلة نفسها. يعيد المساران أخطاء معيارية بـ`429` و`413` و`400` و`502` بدل تمرير استثناءات المزود أو تفاصيله إلى العميل.

> **قرار CORS:** لم يُقدَّم CORS هنا باعتباره طبقة Authorization. APIs المحادثة والتخطيط عامة أصلًا، لذلك أبقى التنفيذ `Access-Control-Allow-Origin: *` بلا cookies وبلا `Access-Control-Allow-Credentials`. جرى تقليص الطرق إلى `POST, OPTIONS` ورأس `Content-Type` فقط. إذا أصبح أحد المسارين خاصًا بالمستخدمين المسجلين لاحقًا، يجب استبدال `*` بقائمة أصول صريحة وإضافة مصادقة خادمية؛ لا يكفي CORS وحده.

### 3. Server-side customer-review protection

أضيف `api/reviews.js` ليكون مسار الإرسال الطبيعي للمراجعات العامة. يتحقق الخادم من حجم الحمولة (8 KiB)، الاسم (2–90 حرفًا)، التقييم (عدد صحيح من 1 إلى 5)، ونص المراجعة (10–1,200 حرف). كما يضيف حقل honeypot؛ عند امتلائه يعيد نجاحًا محايدًا `202` ولا يرسل شيئًا إلى Supabase، ويقيد الإرسال إلى 3 طلبات لكل IP كل 10 دقائق.

لا تستخدم هذه النقطة service-role key ولا تتجاوز RLS. تستعمل publishable key فقط وترسل الحقول الثلاثة الضرورية إلى جدول `customer_reviews`؛ ومن ثم تظل سياسة RLS القائمة هي صاحب القرار في إنشاء السجل، وتبقى دورة moderation الحالية وواجهة الإدارة بلا تغيير. عُدّل `js/customer-reviews.js` ليستخدم المسار الجديد مع الإبقاء على نموذج الواجهة ورسائل المستخدم والتبريد المحلي.

| بند حماية المراجعات | Before | After |
|---|---|---|
| نقطة الكتابة | عميل المتصفح إلى Supabase | `/api/reviews` ثم Supabase publishable API |
| التحقق الخادمي | لا | أحجام وأنواع وحدود نصية محددة |
| مكافحة bots | تبريد محلي فقط | honeypot + rate limit خادمي محلي |
| RLS/moderation | سياسات قائمة | محفوظة، ولا يوجد bypass أو schema change |
| استجابة فشل upstream | غير موحدة من العميل | خطأ `502` لا يكشف تفاصيل المزود |

## Tests and Verification

نفذت مجموعة الاختبارات الكاملة باستخدام `node --test tests/*.test.mjs`. النتيجة النهائية هي **10 اختبارات ناجحة و0 فاشلة**. أُجري أيضًا `node --check` على الوحدات الخادمية والمعدلة، و`git diff --check` للتحقق من خلو الفارق من أخطاء whitespace.

| مجموعة التحقق | النتيجة | ما الذي تثبته |
|---|---|---|
| اختبارات المشروع السابقة | ناجحة | استمرار Admin State وNotion Admin وState Architecture |
| API security tests | ناجحة | رفض الطرق غير المسموح بها، OPTIONS/CORS، رفض المدخلات غير الصالحة أو الضخمة قبل المزود، وحدود AI، والـhoneypot والمراجعات الصحيحة |
| اختبار `vercel.json` | ناجح | وجود CSP و`nosniff` و`DENY` وHSTS في إعداد المصدر |
| Syntax checks | ناجحة | سلامة بناء الوحدات المعدلة في Node |
| `git diff --check` | ناجح | لا أخطاء whitespace في التغييرات |
| Browser smoke test المحلي | ناجح ضمن النطاق | تحميل الصفحة العامة وظهور زر مراجعة العملاء بلا ملء أو إرسال بيانات |

التحقق اليدوي تم من `http://localhost:4173/` فقط. ظهرت الصفحة العامة بنجاح، وبقيت واجهة المراجعات ظاهرة وقابلة للاختيار. لم تُدخل بيانات في نماذج ولم تُرسل مراجعة أو استفسار أو طلب AI. لا يطبق خادم Python الثابت ترويسات Vercel ولا ينفذ serverless functions؛ لذلك لا يمثل اختبار إنتاج end-to-end. يلزم نشر التغيير ثم فحص الترويسات على نطاق النشر واختبار API في preview أو production ببيانات اختبار آمنة.

## Preserved Security Boundaries

ظل فصل **Client UI ≠ Authorization Boundary** قائمًا. لم تُنقل صلاحيات Admin إلى JavaScript، ولم يُغير `private.is_admin()` أو سياسات RLS أو grants أو storage policies أو أي table/view/function في Supabase. Admin Copilot حافظ على الفصل بين AI Pre-fill وDirect Actions، وتظل عمليات الإدارة محمية بالتحقق الخادمي والتفويض الموجودين قبل هذا العمل.

| عملية إدارية | الحد الفعلي بعد التحصين | التغيير |
|---|---|---|
| قراءة/إنشاء/تحديث/حذف بيانات الإدارة | Supabase Auth + RLS و`private.is_admin()` حسب السياسات الحية المدققة سابقًا | لا تغيير |
| نشر المحتوى | عمليات الإدارة المصرح لها عبر RLS/الخادم | لا تغيير |
| إدارة المديرين | مسار Notion Admin الخادمي والتحقق القائم | لا تغيير |
| AI Pre-fill | مسودة تخضع للمراجعة البشرية في العميل الإداري | لا تغيير |
| Direct Actions | مسار منفصل بتفويض خادمي قائم | لا تغيير |

## Remaining Risks and Required Follow-up

التحصين خفّض المخاطر التي يمكن علاجها داخل المستودع، لكنه لا يلغي القيود التشغيلية التالية. لا ينبغي اعتبار أي منها مغلقًا قبل تنفيذ مالك النظام للخطوة المقابلة.

| المخاطرة المتبقية | المستوى | سبب البقاء | الإجراء التالي الموصى به |
|---|---|---|---|
| Supabase leaked-password protection معطلة | متوسط | إعداد Auth حي خارج المستودع | تفعيلها من Supabase Dashboard بعد موافقة مالك النظام |
| rate limits محلية لكل مثيل Serverless | متوسط | Map في الذاكرة لا يتشاركها كل instance وقد تصفر عند cold start | إضافة limit موزع مثل Vercel KV/Upstash بعد قرار تكلفة وتشغيل منفصل |
| AI public endpoints ما زالت عامة | متوسط | مقصود وظيفيًا؛ لا توجد مصادقة للمستخدم النهائي | مراقبة `429`/تكلفة المزود؛ استخدام CAPTCHA أو per-user quota إذا زاد الإساءة |
| `Access-Control-Allow-Origin: *` لمسارات AI/reviews العامة | منخفض | متوافق مع المسارات العامة وبدون credentials؛ CORS ليس تفويضًا | نقلها إلى allowlist إذا أصبحت المسارات خاصة أو تحمل session cookies |
| `'unsafe-inline'` في CSP | متوسط | توافق مع HTML/JS/CSS المضمن الحالي | فصل inline scripts/styles واستخدام hashes أو nonces ضمن مشروع منفصل واختبار كامل |
| لم يحدث نشر أو اختبار بيئة Vercel حية | متوسط | الطلب لم يتضمن commit/push/deploy | نشر إلى preview، فحص ترويسات HTTPS وCSP، ثم اختبار endpoints بحد أدنى |
| حماية المراجعات تعتمد أيضًا على IP | منخفض إلى متوسط | NAT والبوتات الموزعة يمكنها تجاوز حد الذاكرة المحلي | CAPTCHA/Turnstile وlimit موزع عند ارتفاع حجم الإساءة |
